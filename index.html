Walrus x Tatum Hackathon: Total Recall

Receipts: teaching an app to remember who was right

How I used Walrus Memory and Tatum to turn predictions into a track record you can trust.

By TIHLUMINA · November 2026

Watch the 2-minute demo · Try the live app · Read the code

The problem

Everyone online makes predictions. An analyst calls a price target, a tipster backs a team, a friend swears a coin is about to run. A week later the loud calls that missed are forgotten, and the lucky ones are remembered forever. Nobody keeps score, and an app that forgets everything between sessions can’t keep score either.

That is the gap Receipts fills.

What Receipts does

You log a call, such as “SUI will be at or above $1 by Friday, 70% sure.” When the deadline passes, the app checks the real price and prints a receipt stamped HIT or MISS. Every result updates that source’s trust score, and those scores answer a simple question: when sources disagree, who should you believe?

How it uses Walrus Memory

  • Every call and every result is stored as its own memory on mainnet, written with remember and read back with recall.
  • Each source gets its own namespace, so a reputation is built only from that source’s history.
  • Every write returns a blob ID. It is printed on the receipt and used to generate the receipt’s barcode.
  • Trust scores are never stored. They are recomputed from recalled memories on every request.

That last choice is the whole point. If the memory changes, the product’s behavior changes. The learning lives in Walrus, not in the page.

How it uses Tatum

  • The Tatum Data API supplies the price at resolution time, which decides HIT or MISS.
  • The Tatum Sui GraphQL gateway supplies the latest checkpoint, stamped on every result. The resolver also supports wallet-balance claims through the same gateway.
A lesson from the build. My first Sui calls used JSON-RPC and came back 404. Asking the gateway’s /_methods endpoint what it supports showed a GraphQL endpoint only, so I moved every Sui read into one function. The checkpoint is a timestamp anchor to Sui’s state at the moment of checking. It does not prove the price itself.

How it learned over time

Callers state how confident they are. Trust is built from a Brier score, which measures the gap between stated confidence and what happened, then blended with a neutral starting point so one lucky call can’t make anyone look great. Every source starts at 75. A confident miss costs more than a cautious one.

Then the part that shows memory changing the product. Ask two sources the same question. With memory off, they count equally. With memory on, each answer is weighted by the track record recalled from Walrus, so the result moves toward the more reliable source. If every source has the same record, memory moves nothing, which is the honest answer.

What was hard

Walrus Memory is in beta, and one write ran past the SDK’s 60-second wait. The error was clear: the job was still running, and re-sending would have stored it twice. Recall is semantic search, so I tagged each memory with a prefix and parsed the results myself. Both were manageable, and both are worth knowing before you build.

Limits, and what is next

  • The price is read when you press Resolve, not at the exact deadline. The delay is saved with each result.
  • Sources are names, not verified identities, and the demo analysts are fictional.
  • Next: scheduled resolution at each deadline, historical price at the exact deadline, wallet-balance calls in the form, and pay-per-lookup trust scores with x402 on Sui.
